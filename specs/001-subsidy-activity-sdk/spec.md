## Clarifications

### Session 2026-01-06

- Q: 本轮是否需要多项目/登录控制台？ → A: 本轮以单项目演示为主，控制台不需要登录；多项目与权限仅作为未来扩展背景。
- Q: 同一用户对同一活动的领取次数如何限制？ → A: 每用户每活动仅可领取一次。
- Q: 活动在演示页面的展示方式如何区分状态？ → A: 展示可领取活动，并单独列出已暂停/已结束的活动。
- Q: 补贴账户配置允许保存哪些内容？ → A: 仅保存公开地址与可选备注，不保存任何敏感信息。
- Q: 活动完成后的发券触发方式？ → A: 演示页面点击“完成任务”即视为完成并发券。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 项目方配置补贴账户与签到开关 (Priority: P1)

项目方进入控制台，在不提交敏感信息的前提下完成补贴账户配置，并可随时开启或关闭每日签到获得消费券的活动。

**Why this priority**: 补贴账户配置是项目方接入补贴能力的前置条件，签到开关体现活动策略调整的核心诉求。

**Independent Test**: 仅通过控制台完成补贴账户配置与签到开关切换即可验证该故事价值。

**Acceptance Scenarios**:

1. **Given** 项目方进入控制台，**When** 填写补贴账户的公开信息并保存，**Then** 控制台展示配置结果且不要求提交任何密钥等敏感字段。
2. **Given** 每日签到活动处于开启状态，**When** 项目方关闭签到活动，**Then** 演示页面同步显示签到不可用并给出英文错误提示。

---

### User Story 2 - 项目方管理活动并驱动演示领券 (Priority: P1)

项目方在控制台创建、启停或删除活动，设置活动名称、起止时间、消费券类型与总数量；演示页面实时展示活动并允许用户点击完成任务领取消费券。

**Why this priority**: 活动能力是演示“补贴 + 运营增长”的核心场景，需完整串联控制台与演示页。

**Independent Test**: 在控制台创建一个活动并在演示页完成领取，即可独立验证活动闭环。

**Acceptance Scenarios**:

1. **Given** 项目方创建了一个活动，**When** 演示页面刷新或自动同步，**Then** 活动卡片展示名称、时间、奖励类型与剩余数量。
2. **Given** 活动处于开启且未达总量，**When** 用户点击“完成任务”按钮，**Then** 系统发放对应消费券并在列表中可见。
3. **Given** 活动已暂停或已结束，**When** 用户点击领取按钮，**Then** 领取失败并显示英文错误提示。

---

### User Story 3 - 项目方使用SDK快速接入补贴与活动 (Priority: P2)

项目方集成 SDK，在尽量少改动现有系统的情况下，实现指定交易补贴、自动遵循控制台开关、基于消费券 NFT 的抵扣，以及活动驱动的消费券发放与转赠/销毁。

**Why this priority**: SDK 是产品化接入的核心载体，决定项目方能否快速上线补贴功能。

**Independent Test**: 使用 SDK 完成一次补贴交易与一次活动发券，即可证明接入能力。

**Acceptance Scenarios**:

1. **Given** SDK 已完成初始化，**When** 项目方提交指定交易请求，**Then** SDK 按控制台补贴开关决定是否补贴。
2. **Given** 用户持有消费券 NFT，**When** 项目方触发补贴交易，**Then** SDK 能自动识别并走消费券抵扣路径。
3. **Given** 控制台存在一个可领取活动，**When** SDK 触发活动发券流程，**Then** 发放的消费券类型与活动配置一一对应。

---

### Edge Cases

- 当补贴账户尚未配置或配置无效时，控制台如何提示并阻止相关操作？
- 活动总数量为 0 或已发放完毕时，演示页面如何展示并阻止领取？
- 活动被删除但用户页面尚未刷新时，如何避免重复领取或错误显示？
- 每日签到活动关闭后，用户尝试签到时如何提示？
- SDK 在不支持网络或补贴开关关闭时如何返回可读错误？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 控制台 MUST 支持项目方配置补贴账户的公开信息（如地址、备注），且不得要求提交密钥等敏感信息。
- **FR-002**: 系统 MUST 不保存、不过度收集项目方补贴账户的敏感信息，且不得在日志中记录敏感字段。
- **FR-003**: 控制台 MUST 提供每日签到活动的开启/关闭开关，并在演示页面实时可见。
- **FR-004**: 控制台 MUST 允许项目方创建活动，并配置活动名称、起止时间、消费券类型与总数量。
- **FR-005**: 控制台 MUST 支持活动的开启、停止与删除操作，且操作结果在演示页面可见。
- **FR-006**: 演示页面 MUST 展示当前可参与的活动，并提供“完成任务”按钮触发领取。
- **FR-007**: 用户 MUST 只能领取活动允许范围内的消费券，超出总量或已结束/暂停的活动不得领取。
- **FR-008**: 同一用户在同一活动中 MUST 仅能成功领取一次消费券。
- **FR-009**: 系统 MUST 将活动发券与活动配置一一对应，保持奖励类型一致。
- **FR-010**: SDK MUST 支持对指定交易发起补贴请求并返回可读结果。
- **FR-011**: SDK MUST 根据控制台补贴开关自动决定是否执行补贴逻辑。
- **FR-012**: SDK MUST 能根据用户是否持有消费券 NFT 决定是否走抵扣路径。
- **FR-013**: SDK MUST 支持消费券的发放、转赠与销毁操作，以便项目方接入运营活动。
- **FR-014**: SDK 中的活动发券流程 MUST 与控制台活动配置保持一致。
- **FR-015**: 新增功能 MUST 包含单元测试与页面级 E2E。
- **FR-016**: 前端页面文案 MUST 为中文，错误提示 MUST 为英文。

### Key Entities *(include if feature involves data)*

- **项目配置**: 项目方在控制台维护的配置集合（补贴账户公开信息、活动开关）。
- **活动**: 项目方创建的运营活动，包含名称、起止时间、券类型、总数量、状态。
- **活动领取记录**: 用户对活动的领取信息，用于限制重复领取与统计。
- **SDK 配置**: 项目方接入 SDK 时使用的非敏感标识信息与权限范围。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 项目方可在 3 分钟内完成补贴账户配置并成功保存。
- **SC-002**: 新建活动在 5 秒内出现在演示页面并可领取。
- **SC-003**: 活动领取成功率达到 95% 以上（在活动有效且未超量的情况下）。
- **SC-004**: SDK 接入方可在 30 分钟内完成一次补贴交易与一次活动发券演示。

## Assumptions

- 演示环境默认单项目场景，控制台无需登录访问，多项目与权限仅作为未来扩展背景。
- 活动时间以 Asia/Shanghai 自然时区为准。
- 活动领取默认每用户每活动仅一次，领取总量达到上限后活动自动不可领取。
